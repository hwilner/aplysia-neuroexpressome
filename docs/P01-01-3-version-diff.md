# P01-01.3 — build the image a second time and diff the tool versions

**Parent:** P01-01. **Status:** in progress. **Started:** 2026-11-02.

## What the subtask asks

Build the image a second time and diff the tool versions. The point is to
establish that the pins produce the same image twice, so that a result
produced later can be tied to a known set of tool versions.

## Why this is not a one-line step

The first thing that had to be settled was *what a version diff would compare*.
The manifest that P01-01.2 produced, recorded in
`docs/environment-manifest-2026-10-29.txt`, is green-build evidence and it
contains four defects:

```
hmmsearch       Failed to parse command line: No such option "--version".
emapper.py      There was an error retrieving eggnog-mapper DB data: not a valid file "..."
orthofinder     (empty)
trimal          (empty)
```

The manifest was generated by running `--version` on every command and
recording whatever came back. Two of the tools do not have that flag, one of
them fails because its database is not shipped in the package, and two print
nothing at all. The build gate looked for the string `NOT FOUND` and passed
every one of them.

So the diff P01-01.3 asks for would have compared error messages and empty
strings, and two builds with identical failures would have "agreed". The
comparison would have been green and would have meant nothing.

## What was changed

**`scripts/manifest.py` generates the manifest now.** Each tool gets a list
of candidate invocations; the output is validated, and a value that is empty
or reads as an error is rejected. When no candidate yields a usable version,
the version of the conda package that provides the command is used instead.
That fallback cannot fail, because the package is in the image by
construction. The manifest also carries `micromamba list` output for every
environment: the direct pins are a dozen packages, what is installed is their
whole transitive closure, and that closure is what has to be identical
between two builds.

**`scripts/diff_manifests.py` does the comparison.** It excludes the build
timestamp, and it excludes nothing else — and it reports how many lines it
excluded, so the exclusion is visible rather than silent. It also fails a
comparison in which either manifest carries an unusable version, which is the
failure mode the old manifest had.

**The Dockerfile's manifest stage now calls the script** and fails the build
if it cannot write the manifest. The previous stage swallowed its own errors
with `|| true`, which is how an image with no manifest at all got shipped.

**The CI workflow gained a second, independent build.** A rebuild inside the
same job would share the runner's base-image layers and its build cache, so it
would be a comparison of a build with itself. `rebuild` is a separate job on
a separate runner with `--no-cache`, and `version-diff` compares the two
manifests.

## What is verified and what is not

Verified locally, without a container:

- 32 unit tests pass, including one that runs the recorded green manifest
  through the checker and asserts that the defective set is exactly those
  four tools. If a future manifest is worse, the test fails; if it is
  better, the test fails and has to be updated deliberately.
- The checker reports 25 tool lines and 4 unusable in the recorded manifest.
- The drift test caught a real gap while it was being written: `biopython`
  was pinned and no tool reported its version. It now does.

Not yet verified: whether the rebuilt image actually agrees with the first
one. That needs the CI run, which is the point of the subtask.

## Note for the next person

The interesting failure here was not a dependency conflict. It was a check
that passed because it looked for the wrong string. A build gate that
searches for `NOT FOUND` reports on the failures it knows about and stays
silent about the ones it does not, and a green build with a broken manifest
is worse than a red one, because it is believed.
